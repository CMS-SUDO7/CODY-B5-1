## 1. 먼저 알아야 할 기초

### DB 파일·DBMS·SQL·실행 도구를 구분하기

데이터베이스(DB, Database)는 일정한 구조와 규칙으로 저장한 데이터의 모음입니다. DBMS(Database Management System)는 이를 저장·조회·수정하는 소프트웨어입니다. SQL(Structured Query Language)은 관계형 DBMS에 원하는 작업을 전달하는 언어입니다.

이번 실습에서는 `cafe.db`가 데이터를 담은 파일이고, SQLite가 그것을 다루는 DBMS입니다. SQL 편집기나 터미널 도구는 사람이 SQL을 입력하고 결과를 보는 창입니다. 파일을 받는 것과 실행 도구를 준비하는 것은 서로 다른 일입니다.

SQLite는 서버 프로세스를 따로 띄우지 않고 로컬 파일을 다룰 수 있습니다. 그래서 관계와 SQL 자체를 먼저 공부하는 이번 미션에 사용했습니다.

### 표의 행·열과 자료형

행은 대상 한 건, 열은 대상의 속성입니다. 고객 표에서 한 행은 고객 한 명이고 이름·이메일은 각각 열입니다. 전체 이름 목록을 읽는 것과 특정 고객 한 명을 찾는 것은 각각 열 선택과 행 선택에 해당합니다.

이번 실습은 금액과 수량에 `INTEGER`, 이름과 날짜 문자열에 `TEXT`를 사용합니다. 금액은 원 단위 정수로 저장해 소수 계산에서 생기는 반올림 오차를 피합니다.

SQLite 일반 테이블은 타입을 유연하게 처리합니다. `INTEGER` 선언만으로 모든 비정수 입력이 차단되지는 않습니다. 날짜도 같은 `YYYY-MM-DD HH:MM:SS` 형식으로 저장한다는 약속이 있어야 문자열 비교와 시간 순서가 맞습니다. 현재 스키마는 날짜 형식 자체를 검사하지 않습니다.

### 엑셀과 DB를 비교할 때 볼 점

엑셀도 표를 연결하고 분석할 수 있습니다. 차이를 단순히 데이터 양이나 “엑셀에는 관계가 없다”는 말로 외우지 마세요. 이번에는 DB가 **키와 제약조건을 통해 데이터 사이의 관계를 지킨다**는 점에 집중합니다.

예를 들어 주문표에 고객 이름을 매번 쓰면 이름 변경 때 여러 행을 고쳐야 합니다. 고객 정보를 한곳에 저장하고 주문에서는 고객 번호를 참조하면 이런 불일치를 줄입니다. 없는 고객 번호의 주문은 DB가 거부하도록 만들 수 있습니다.

### 실행 순서와 초기 상태

구조 만들기 → 부모 데이터 넣기 → 자식 데이터 넣기 → 조회·변경 순서로 진행합니다. 참조할 고객이 먼저 있어야 그 고객의 주문을 넣을 수 있습니다.

제공 DB에는 고객 10명, 메뉴 10개, 주문 14건, 상세 23행이 들어 있습니다. 질문을 풀 때는 초기 DB 복사본을 사용하세요. 수정·삭제 후 같은 조회를 실행하면 결과가 달라질 수 있습니다.

## 2. 미션에서 사용하는 용어

### 스키마와 데이터 모델: 무엇을 어떻게 저장할지 정하기

**기본 설명**

데이터 모델은 어떤 대상을 나누고 어떻게 연결할지 정한 구조입니다. 스키마는 이를 테이블·열·타입·제약조건으로 정의한 것입니다. 이 문서에서 도메인은 저장하려는 업무 분야, 즉 카페 주문을 뜻합니다.

**비유 설명**

서랍장 설계에서 어떤 칸을 만들고 각 칸에 무엇을 넣을지 정하는 것과 비슷합니다. 다만 DB의 칸들은 번호로 연결되며, 관계와 입력 규칙을 DB가 검사할 수 있습니다.

**작은 예시**

고객의 이름은 고객표에, 주문 시각은 주문표에, 주문한 메뉴와 수량은 상세표에 둡니다. 실제로 어떤 테이블을 만들었는지는 실행 안내의 관계도에서 확인할 수 있습니다.

### PK: 행 하나를 구별하는 기본 키

**기본 설명**

PK(Primary Key, 기본 키)는 한 행을 유일하게 구별합니다. 이름이 같은 고객도 서로 다른 고객 번호로 구분할 수 있습니다. 이번 스키마의 `INTEGER PRIMARY KEY`는 SQLite 내부 행 식별자인 rowid와 연결됩니다.

**비유 설명**

같은 이름의 학생을 학번으로 구분하는 것과 같습니다. 학번에 대응하는 것이 고객 번호입니다. 다만 고객 번호 자체가 고객의 실명이나 나이를 뜻하지는 않습니다.

**작은 예시**

고객 1번과 고객 2번은 서로 다른 행입니다. 중간 행을 삭제했다고 나머지 번호를 다시 매기지 않습니다. 가장 큰 번호와 전체 행 수는 다를 수 있습니다.

### FK와 부모·자식: 다른 표의 행을 참조하기

**기본 설명**

FK(Foreign Key, 외래 키)는 다른 테이블의 키를 참조하는 규칙입니다. 참조받는 쪽을 부모, 참조하는 쪽을 자식이라고 부릅니다. 여기서는 고객이 부모이고 그 고객 번호를 저장하는 주문이 자식입니다.

**비유 설명**

주문서에 적은 회원 번호를 회원 명부와 대조하는 것과 같습니다. 명부에 없는 번호를 적으면 주문을 받지 않는 규칙이 FK 검사입니다.

**작은 예시**

주문에 고객 번호 1을 넣으려면 고객 1번이 존재해야 합니다. 고객 999번이 없는데 그 번호를 참조하면 입력이 거부됩니다. 고객 번호만 같은 것이 아니라, 스키마에 FK를 선언하고 검사를 켜야 합니다.

### 1:N·N:M·연결 테이블: 관계의 개수 표현하기

**기본 설명**

1:N(일대다)은 한쪽의 행 하나가 다른 쪽의 여러 행과 연결되는 관계입니다. 고객 한 명은 주문 여러 건을 만들 수 있지만, 이번 설계에서 주문 한 건은 고객 한 명에게 속합니다. 여러 주문의 FK 값이 같을 수 있으므로 FK가 항상 UNIQUE인 것은 아닙니다.

N:M(다대다)은 양쪽 모두 여러 행과 연결될 수 있는 관계입니다. 주문에는 여러 메뉴가 들어가고, 메뉴도 여러 주문에 등장합니다. 이를 주문 상세라는 연결 테이블로 풀었습니다.

**비유 설명**

영수증 한 장에 메뉴가 여러 줄 있고, 같은 메뉴가 다른 영수증에도 나오는 상황입니다. 영수증의 각 줄에 대응하는 것이 주문 상세입니다.

**작은 예시**

1번 주문에 아메리카노 2개와 케이크 1개가 들어가면 상세는 2행입니다. 수량의 합인 3과 상세 행 수인 2를 구분해야 합니다. 같은 주문·메뉴 조합은 한 줄로 두고 수량에 합칩니다.

### 무결성과 제약조건: 저장해도 되는 값의 규칙

**기본 설명**

무결성(integrity)은 데이터가 정해 둔 규칙을 지키는 성질입니다. 제약조건(constraint)은 DB가 이를 검사하도록 선언한 규칙입니다.

| 규칙 | 하는 일 | 이번 실습의 예 |
| --- | --- | --- |
| `PRIMARY KEY` | 행을 유일하게 구별 | 중복 고객 번호 차단 |
| `NOT NULL` | 값 누락 차단 | 고객 이름 NULL 차단 |
| `UNIQUE` | 같은 값·조합의 중복 차단 | 이메일, 주문·메뉴 조합 |
| `CHECK` | 지정 조건 검사 | 수량 양수, 상태 허용 목록 |
| `FOREIGN KEY` | 참조 관계 검사 | 없는 고객의 주문 차단 |

**비유 설명**

접수 창구의 확인 항목과 비슷합니다. 이름 기재, 중복 접수, 등록 회원 여부는 각각 다른 검사입니다. 한 검사에 통과했다고 모든 조건을 만족한 것은 아닙니다.

**주의할 점**

NOT NULL은 빈 문자열을 막지 않으며, 이메일 UNIQUE는 이메일 형식 검증이 아닙니다. SQLite에서 UNIQUE만 선언한 열은 NULL 여러 개를 허용할 수 있으므로 필수 이메일에는 NOT NULL도 함께 적용했습니다.

### 연결·PRAGMA·RESTRICT: SQLite에서 관계 지키기

**기본 설명**

연결(connection)은 도구가 DB를 열고 작업하는 통로입니다. `PRAGMA`는 SQLite 설정·정보를 다루는 전용 명령입니다. FK 검사는 사용하는 연결마다 `PRAGMA foreign_keys = ON;`으로 켜고 1인지 확인합니다. 트랜잭션을 시작하기 전에 설정해야 합니다.

`ON DELETE RESTRICT`는 참조하는 자식이 남아 있으면 부모 삭제를 막는 규칙입니다. 검사 기능을 꺼서 삭제를 통과시키는 것이 해결책은 아닙니다.

**비유 설명**

창구를 새로 열 때마다 회원 대조 절차를 켜는 것과 비슷합니다. 다른 창구에서 켰다고 현재 창구의 검사도 켜진 것은 아닙니다.

**작은 예시**

상세가 있는 1번 주문 삭제는 거부됩니다. 상세가 없는 14번 취소 주문은 삭제할 수 있습니다. 주문이 남아 있는 고객이나 상세에 쓰인 메뉴 삭제도 막습니다.

### CRUD·DDL·쿼리: 데이터에 요청하는 작업

**기본 설명**

쿼리(query)는 DB에 보내는 질의나 작업 요청입니다. 이 과제의 “핵심 쿼리 15개”에는 조회뿐 아니라 수정·삭제·인덱스 생성도 포함됩니다.

CRUD는 Create(생성)·Read(읽기)·Update(수정)·Delete(삭제)를 묶은 말입니다. 행에 대한 CRUD와 테이블 자체를 만드는 작업은 구분합니다. 구조를 정의하는 CREATE TABLE·CREATE INDEX는 DDL(Data Definition Language, 데이터 정의 언어)에 해당합니다.

| 목적 | SQL | 결과에 미치는 영향 |
| --- | --- | --- |
| 새 행 추가 | `INSERT` | 행 수가 늘어남 |
| 기존 행 읽기 | `SELECT` | 조회 결과를 만들며 원본 행은 유지 |
| 기존 행 수정 | `UPDATE` | 조건에 맞는 값이 바뀜 |
| 기존 행 삭제 | `DELETE` | 조건에 맞는 행이 사라짐 |

**비유 설명**

고객 명부에 새 카드를 꽂기, 읽기, 내용을 고치기, 빼내기가 행의 CRUD입니다. 명부에 어떤 항목을 둘지 틀을 만드는 것은 구조 정의에 해당합니다.

### WHERE·검색·정렬·LIMIT: 결과 범위 정하기

**기본 설명**

WHERE는 조건을 만족하는 행을 남깁니다. AND는 조건을 모두 만족할 때 참이고, IN은 목록 중 하나와 일치하는지 검사합니다. LIKE는 문자열 패턴을 비교하며 `%`는 길이가 0 이상인 문자열에 대응합니다.

ORDER BY는 결과 순서를 정합니다. ASC는 오름차순, DESC는 내림차순입니다. LIMIT은 그 결과에서 반환할 행 수를 제한합니다. 정렬 없이 LIMIT만 써서는 최신 항목을 보장할 수 없습니다.

**작은 예시**

`LIKE '%라테%'`는 이름 중간에 라테가 있어도 찾습니다. “10월 주문을 최신순으로 정렬한 뒤 5건”과 “아무 주문 5건”은 다른 요구입니다. 같은 시각이면 주문 번호를 두 번째 정렬 기준으로 사용합니다.

### JOIN: 나눈 데이터를 다시 연결하기

**기본 설명**

JOIN은 연결 조건에 맞는 행을 조합합니다. INNER JOIN은 짝이 있는 행을 반환합니다. LEFT JOIN은 왼쪽 행을 보존하고 짝이 없으면 오른쪽 열을 NULL로 채웁니다. ON에는 어느 열끼리 연결할지 적습니다.

**비유 설명**

회원 명부와 주문서를 회원 번호로 맞춰 펼치는 것과 같습니다. 명부의 모든 회원을 먼저 놓고 주문서를 붙이면 주문 없는 회원도 남는데, 이것이 LEFT JOIN의 핵심입니다.

**작은 예시**

1번 고객의 주문이 두 건이면 연결 결과에 고객 이름도 두 번 나타납니다. 9번 고객은 주문이 없어 LEFT JOIN 결과의 주문 번호가 NULL입니다. JOIN은 원본 표를 영구 합치는 작업이 아닙니다.

### GROUP BY와 집계 함수: 여러 행을 요약하기

**기본 설명**

GROUP BY는 기준이 같은 행을 묶습니다. 집계 함수는 그룹의 여러 값을 받아 개수·합계·평균 등의 요약값을 만듭니다. WHERE로 대상 행을 정한 뒤 그룹별 값을 계산합니다.

| 실제 사용 함수 | 계산 대상 | 역할 |
| --- | --- | --- |
| `COUNT(*)` | 그룹의 모든 행 | 상태별 주문 건수 |
| `SUM(수량 × 당시 단가)` | 그룹의 상세 소계 | 고객별 구매액 |
| `AVG(가격)` | 그룹의 NULL이 아닌 가격 | 분류별 메뉴 평균 가격 |

`ROUND(값, 2)`는 여러 행을 묶는 집계 함수가 아니라, 계산된 값 하나를 소수 둘째 자리로 반올림하는 함수입니다. 위 이름들은 SQL 함수이며 Python 내장 함수 목록에 넣지 않습니다.

**비유 설명**

영수증을 고객별 상자에 모은 뒤 상자마다 금액을 더하는 것과 같습니다. 상자를 나누는 기준이 GROUP BY, 금액을 더하는 작업이 SUM입니다.

**작은 예시**

결제 완료 주문을 고른 뒤 고객별로 상세 금액을 더하면 고객별 구매액이 나옵니다. 반면 메뉴 평균 가격은 메뉴를 하나씩 같은 비중으로 평균 낸 값이며 주문 수량을 반영한 평균이 아닙니다.

### NULL과 COUNT: 값 없음과 숫자 0 구분하기

**기본 설명**

NULL은 값이 없거나 알려지지 않은 상태입니다. 숫자 0이나 빈 문자열과 다릅니다. NULL 여부는 `IS NULL` 또는 `IS NOT NULL`로 검사합니다. `= NULL`을 일반적인 값 비교처럼 사용하지 않습니다.

COUNT(*)는 결과 행을 세고 COUNT(열)는 그 열이 NULL이 아닌 행을 셉니다. 따라서 LEFT JOIN 뒤에 무엇을 세는지에 따라 답이 달라집니다.

**비유 설명**

주문서 칸이 빈 회원 카드와, 금액 0원이 적힌 주문서는 다른 상태입니다. 다만 NULL에는 여러 의미가 있을 수 있으므로 실제 데이터의 문맥을 함께 봐야 합니다.

**작은 예시**

주문 없는 고객도 LEFT JOIN 결과에는 한 행 남습니다. 그 한 행을 COUNT(*)하면 1이지만, NULL인 주문 번호를 COUNT하면 0입니다. 원래 주문 수를 세려는 조회에서는 이 차이가 중요합니다.

### 서브쿼리·상관 서브쿼리·NOT EXISTS

**기본 설명**

서브쿼리는 다른 SQL 안에 들어간 조회입니다. 그 안에서 바깥 조회의 현재 행을 참조하면 상관 서브쿼리라고 합니다. NOT EXISTS는 내부 조회가 한 행도 찾지 못할 때 참입니다.

**비유 설명**

회원 한 명을 확인할 때마다 주문 명부에 그 회원의 주문서가 있는지 대조하고, 없는 회원만 따로 적는 과정과 같습니다. 이는 결과를 이해하기 위한 과정이며 DB 엔진의 물리 실행 순서를 단정하는 설명은 아닙니다.

**작은 예시**

고객 9번을 기준으로 주문을 찾으면 0행이므로 결과에 남습니다. 고객 1번은 주문이 있어 제외됩니다. 내부의 `SELECT 1`에서 1은 고객·주문 번호가 아니라 존재 확인용 상수입니다.

### 별칭과 소계: 긴 조회에 이름 붙이기

**기본 설명**

별칭(alias)은 SQL 안에서 테이블이나 결과 열을 잠시 부를 이름입니다. `cafe_order AS o`는 주문 테이블을 o로 부른다는 뜻입니다. `AS subtotal_won`은 계산 결과 열의 이름을 정합니다. 원본 테이블 이름이나 저장 데이터는 바꾸지 않습니다.

소계는 전체 합계에 들어갈 일부 금액입니다. 이번에는 상세 한 행의 수량에 당시 단가를 곱한 값이 소계입니다.

**작은 예시**

아메리카노 2개 × 4,000원은 소계 8,000원입니다. 소계들을 SUM하면 주문별 또는 고객별 합계가 됩니다. 어떤 기준으로 묶는지에 따라 합계의 의미가 달라집니다.

### 트랜잭션·COMMIT·ROLLBACK: 변경 확정하기

**기본 설명**

트랜잭션(transaction)은 함께 확정하거나 되돌릴 작업 단위입니다. BEGIN으로 시작하고 COMMIT으로 확정하며, 확정 전에는 ROLLBACK으로 취소할 수 있습니다. 이미 확정한 변경은 ROLLBACK으로 되돌릴 수 없습니다.

SAVEPOINT는 트랜잭션 안에 표시해 두는 부분 되돌리기 지점입니다. 검증에서는 실패할 입력마다 이 지점을 두고 되돌려 다른 검사에 영향을 주지 않게 했습니다.

**비유 설명**

여러 항목을 임시 수정한 뒤 한 번에 확정하는 편집 작업과 비슷합니다. 다만 SQL 한 문장에서 오류가 났다고 전체 작업이 자동 취소되는 것은 아닙니다. 실행을 중단하고 열린 작업을 정리해야 합니다.

**작은 예시**

전체 쿼리 파일은 수정·삭제·인덱스 생성을 마지막 COMMIT에서 확정합니다. 초기 상태로 연습하려면 새 DB에 스키마와 샘플을 다시 넣거나 초기 DB 복사본을 사용합니다.

### 인덱스·복합 인덱스·실행 계획

**기본 설명**

인덱스(index)는 특정 값의 행을 찾거나 정렬된 순서로 읽도록 돕는 별도 구조입니다. 두 열 이상을 함께 사용하면 복합 인덱스입니다. 실행 계획은 DB가 데이터를 어떤 방식으로 읽으려는지 보여 줍니다.

**비유 설명**

책 뒤의 찾아보기를 이용하면 찾는 항목이 있는 쪽으로 바로 갈 수 있습니다. DB에서도 특정 값의 구간으로 접근할 수 있지만, 데이터 대부분을 읽어야 하면 처음부터 읽는 편이 나을 수 있습니다.

**작은 예시**

최근 주문 검색은 주문 시각으로 범위를 좁히고 시각·주문 번호 순서로 정렬합니다. 그래서 같은 두 열과 순서로 인덱스를 만들었습니다. 사용한 SQLite의 계획에서 SCAN은 전체 훑기, SEARCH는 조건을 사용한 구간 접근을 나타냅니다. B-tree는 값 순서를 이용해 구간을 찾는 트리 구조이며, 정렬용 임시 B-tree가 보이면 별도의 정렬 작업이 필요하다는 단서입니다.

인덱스는 저장 공간을 사용하고 데이터 변경 때 유지 비용도 듭니다. 계획에서 인덱스 사용을 확인한 것과 처리 시간 단축을 측정한 것은 다른 증거입니다. 이번에는 시간 단축을 측정하지 않았습니다.

## 3. 이번 미션의 핵심

### 문제 1. 정보를 나눴는데 주문에는 어떻게 이름을 보여 줄까?

**문제**: 이름을 주문마다 적으면 고객 이름 변경 시 서로 다른 이름이 남을 수 있습니다. 그렇다고 고객 번호만 보여 주면 사람이 읽기 어렵습니다.

**해결 원리**: 고객 이름은 고객표에 한 번 두고, 주문은 고객 번호만 참조합니다. 화면에 보여 줄 결과를 만들 때 번호가 같은 행을 JOIN합니다.

**작은 예시**: 1번 주문의 고객 번호는 1입니다. 고객 1번의 이름인 김민수를 붙여 “1번 주문, 김민수”라는 결과를 만듭니다. 고객 이름을 수정하면 다음 조회에 새 이름이 연결됩니다.

**선택 이유**: 저장의 중복은 줄이면서 조회 결과에는 필요한 이름을 담을 수 있습니다. 주문 없는 고객까지 확인해야 하는 조회에만 LEFT JOIN을 선택했습니다. 주문·고객 연결은 Q05, 전체 고객 확인은 Q07에서 볼 수 있습니다.

### 문제 2. 메뉴 가격이 바뀌어도 예전 구매액을 지킬 수 있을까?

**문제**: 현재 메뉴 가격만 사용하면 가격 인상 후 예전 주문의 금액까지 달라질 수 있습니다.

**해결 원리**: 주문 당시 단가를 상세에 보존하고, 결제 완료 주문만 골라 소계를 고객별로 합칩니다. 현재 판매 중단된 메뉴도 과거 결제 내역에는 남깁니다.

**작은 예시**: 김민수의 첫 주문은 아메리카노 8,000원 + 케이크 6,500원 = 14,500원입니다. 두 번째는 콜드브루 5,000원 + 쿠키 2,500원 = 7,500원입니다. 고객별 구매액은 22,000원입니다.

**선택 이유**: 고객 이름의 불필요한 중복과, 과거 사실을 보존하는 가격 사본은 목적이 다릅니다. 모든 중복을 없애는 것보다 어떤 사실을 언제 기준으로 저장할지 정하는 것이 중요합니다. 실제 구매액 조회는 Q10입니다.

### 문제 3. 주문 1건이 상세 2줄이면 몇 건으로 세야 할까?

**문제**: 주문과 상세를 연결한 뒤 행 개수를 세면 메뉴 종류 수만큼 주문이 중복 집계될 수 있습니다.

**해결 원리**: 먼저 “한 건”의 기준을 정합니다. 주문 건수는 주문표에서 세고, 매출은 상세의 수량과 당시 단가를 곱해 더합니다.

**작은 예시**: 1번 주문은 상세 2행이고 수량 합계는 3개입니다. 주문 건수는 1건, 상세 행 수는 2행, 상품 개수는 3개입니다. 셋을 같은 숫자로 취급하면 안 됩니다.

**선택 이유**: 무엇을 세는지 먼저 정해야 맞는 테이블과 집계식을 고를 수 있습니다. 상태별 주문 수 조회 Q09는 상세를 JOIN하지 않습니다.

### 문제 4. 검색·정렬·상위 목록을 어떤 순서로 만들까?

**문제**: 전체 주문에서 아무 5건을 뽑으면 최근 10월 주문이 아닐 수 있습니다.

**해결 원리**: 10월 범위를 남기고 최신순으로 정렬한 다음 5건을 선택합니다. 월 범위는 10월 시작 이상·11월 시작 미만으로 둬 마지막 초를 따로 계산하지 않습니다.

**작은 예시**: 초기 데이터의 최근 5건은 주문 번호 14·13·12·11·10 순서입니다. 기간 조회와 정렬 열에 맞춰 인덱스를 만들면 DB가 필요한 구간을 읽는 계획을 선택할 수 있습니다.

**선택 이유**: 시각이 같아도 순서가 일정하도록 주문 번호를 보조 기준으로 넣었습니다. Q03이 검색·정렬, Q15가 이를 돕는 인덱스입니다. 고객 구매액 상위 목록도 먼저 합계를 만들고 금액순으로 정렬합니다. 단순 상위 N행과 공동 순위 전원을 포함하는 순위표는 요구가 다릅니다.

### 문제 5. 수정과 삭제를 확인하면서 연습하려면?

**문제**: 전체 파일을 반복 실행하면 초기 조회 결과와 다른 결과가 나오고 변경 행 수도 0이 될 수 있습니다.

**해결 원리**: 초기 상태와 변경 후 상태를 구분합니다. 수정·삭제는 대상 번호와 현재 상태로 범위를 좁히고, 전후 값을 확인한 뒤 확정합니다.

**작은 예시**: 13번은 pending에서 paid로 바뀝니다. 14번 취소 주문은 상세가 없어 삭제됩니다. 처음 14건이던 주문은 최종 13건입니다. 이미 paid인 13번에 같은 조건의 수정을 다시 실행하면 0행이 바뀝니다.

**선택 이유**: 조회 결과를 직접 비교하면서도 원래 샘플을 다시 만들 수 있습니다. 전체 실습 재시작에는 초기 DB의 새 복사본을 사용합니다. 실행 전후 값은 Q13·Q14의 결과 파일에 있습니다.

다음은 필수 쿼리 15개를 완성한 뒤 해 볼 연습입니다. 아래 수정 예시는 기본 제출 SQL에 추가 구현되어 있지 않습니다.

### 연습 A. 상위 고객 3명만 출력하기

- 목표: 집계와 정렬 뒤 행 수 제한을 적용합니다.
- 시작점: Q10의 마지막 ORDER BY 줄에서 세미콜론을 빼고 `LIMIT 3;`을 붙입니다.
- 확인할 결과: 초기 데이터에서 고객 번호 1·2·3, 구매액은 22,000·22,000·21,500원입니다. 공동 순위 전원 반환과는 다른 요구입니다.

### 연습 B. 주문 없는 고객만 LEFT JOIN으로 찾기

- 목표: 같은 요구를 JOIN과 서브쿼리로 비교합니다.
- 시작점: Q07에 오른쪽 주문 번호가 NULL인 조건을 추가하고, Q12와 결과를 비교합니다.
- 확인할 결과: 두 방식 모두 고객 9·10번을 반환해야 합니다. LEFT JOIN에서 NULL로 채워진 열을 무엇으로 검사할지 생각해 보세요.

### 연습 C. 주문별 총액 만들기

- 목표: 같은 상세 데이터라도 묶는 기준을 바꾸면 다른 지표가 나오는 것을 확인합니다.
- 시작점: Q10을 참고해 고객 대신 주문 번호로 묶고 결제 완료 주문의 상세 소계를 더합니다.
- 확인할 결과: 초기 주문 1번은 14,500원, 4번은 7,500원입니다. 고객별 합계와 혼동하지 않습니다.

### 다음 공부 주제와 현재 한계

- **정규화**: 중복 때문에 여러 곳을 고쳐야 하는 문제를 줄이는 설계 방법입니다. 현재는 고객 정보 분리와 당시 가격 보존의 이유부터 설명하면 충분합니다.
- **동시성**: 여러 사용자의 변경이 겹칠 때 일관성을 지키는 문제입니다. 한 사람이 로컬에서 실행하는 이번 실습 이후에 다룹니다.
- **매개변수 바인딩**: 향후 앱에서 입력값을 SQL 문자열에 이어 붙이지 않고 값으로 전달하는 방법입니다.
- **ORM(Object-Relational Mapping)**: 프로그램 객체와 관계형 테이블을 연결하는 방식입니다. PK/FK와 JOIN의 의미를 먼저 익힙니다.
- **입력·업무 검증**: 날짜와 이메일 형식, 공백 이름, 결제 완료 주문에 상세가 반드시 있는지 등의 규칙은 현재 모두 강제하지 않습니다. FK가 정상이어도 업무상 규칙까지 모두 충족하는 것은 아닙니다.

실제 주문 서비스에는 시간대·세금·할인·부분 환불·접근 제어 등 추가 고려가 필요합니다. 현재는 원 단위 금액과 같은 형식의 로컬 시각 문자열을 사용한 SQL 실습입니다. 원문 범위 밖인 뷰·프로시저·트리거·웹 API는 사용하지 않았습니다.
